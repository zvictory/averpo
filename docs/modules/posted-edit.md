# Ҳужжатни таҳрирлаш ва ўчириш (posted-edit): QBO туйғуси, сторно ядро

ҲОЛАТ: ТАСДИҚЛАНГАН (фойдаланувчи, 2026-07-14). Карта: Arbitr-114
(review/accepted/), changeset 067 БАНД. Навбат ўрни: 113 → 103 дан
КЕЙИН (фойдаланувчи қарори). BR-EDT оиласи business-rules.md
каталогида, posting қоидаси posting-rules.md да.

## Мақсад

Фойдаланувчи POSTED ҳужжатни QBO'дагидек «Таҳрирлаш» тугмаси билан
тузатади ва «Ўчириш» тугмаси билан олиб ташлайди. Ичкарида темир
қоида №3 БУЗИЛМАЙДИ: POSTED ҳужжат ўзгармайди - тизим битта атомик
транзакцияда эски ҳужжатни сторно қилади; таҳрирда устига ЯНГИ
ҳужжат яратиб POST қилади, ўчиришда эса ҳужжатни кўринишлардан
яширади. Фойдаланувчи битта амал кўради, ledger'да тўлиқ из қолади.

## Модель

- Ҳар таҳрир = **версия занжири**: v1 (эски) → v2 (янги) → v3 ...
- Эски версия: статуси REVERSED (мавжуд механизм), янги майдон
  `superseded_by_id` тўлдирилади - «бекор» эмас «алмашган» экани
  шундан билинади. Янги enum қиймат КИРИТИЛМАЙДИ (14 та статус
  enum'ига тегилмайди - энг кичик хавф).
- Янги версия: янги UUID, лекин **ҳужжат рақами МЕРОС** (INV-0012
  INV-0012 лигича қолади - QBO туйғусининг ядроси) + `revision`
  (int, v1=1) ортади. Ноёблик: unique(doc_number) →
  unique(doc_number, revision) га миграция.
- GL'да икки ёзув: сторно JE + янги ҳужжат JE - иккиси ҲАМ янги
  версия санасида (ГИБРИД қоида, BR-EDT-004: сана очиқ даврда бўлиши
  шарт). sum(debitBase) == sum(creditBase) инварианти ҳар иккисида
  одатдагидек.
- Рўйхатларда алмашган (superseded_by_id != null) версиялар DEFAULT
  КЎРИНМАЙДИ - фақат жорий версиялар. Кўриш саҳифасида «Версиялар»
  блоки: v1 (алмашган, санаси) → v2 (жорий) ҳаволалари.
- Аудит: AuditEvent DOCUMENT_EDITED (ким, қачон, қайси ҳужжат,
  v(n)→v(n+1)). Тўлиқ олдин/кейин JSON снапшоти - 2-босқичда.

## Фойдаланувчи оқими

1. POSTED ҳужжат view'ида «Таҳрирлаш» тугмаси (EDIT permission +
   қуйидаги шартлар ўтса; ўтмаса тугма ўрнида сабаб кўринади).
2. Мавжуд форма эски қийматлар билан очилади (DRAFT edit формаси
   қайта ишлатилади - янги форма ёзилмайди).
3. Сақлашда сервер БИТТА транзакцияда: reverse(эски, сабаб
   автоматик: «Таҳрир: <рақам> v<n+1>») + яратиш&post(янги, рақам
   мерос, revision+1) + superseded_by боғлаш.
4. Redirect янги view'га, flash: «Ҳужжат таҳрирланди (v2)».
5. Мавжуд «Сторно» тугмаси ўз жойида қолади (бекор қилиш учун -
   QBO'даги Void ўрнида: ҳужжат кўринади, GL таъсири нолланган).

## «Ўчириш» амали (QBO Delete туйғуси)

- POSTED ҳужжатда «Ўчириш» тугмаси (confirm диалог билан). Ичкарида:
  атомик сторно + ҳужжатга `deleted` белгиси.
- Ўчирилган ҳужжат ҲЕЧ ҚАЕРДА кўринмайди: рўйхатлар, ҳисоботлар,
  drill-down, глобал қидирув - барчасидан яширин. GL'да эса жуфт
  ёзув (асл + сторно, нетто ноль) қолади - аудит изи бузилмайди.
  QBO'дан ягона ички фарқи шу: QBO GL'ни ҳам ўчиради, биз нетто-ноль
  из қолдирамиз; фойдаланувчига натижа бир хил.
- Ўчирилганларни кўриш: фақат аудит журнали орқали (DOCUMENT_DELETED
  ёзуви ҳужжатга ҳавола беради; view'га тўғридан URL билан кирса
  «Ўчирилган» банер кўринади, амал тугмалари йўқ).
- Ҳужжат рақами ҚАЙТА ИШЛАТИЛМАЙДИ (кетма-кетлик олдинга юраверади -
  рақам тешиги аудитда изоҳланади, бу нормал).
- Блок шартлари ТАҲРИР билан БИР ХИЛ (қуйидаги BR-EDT-002/003/004/
  005 ўчиришга ҳам тегишли): тўлов боғланган, reconciled, омбор
  чекловлари - аввал ечилади.
- DRAFT ўчириш одатдагидек қолади (GL йўқ - ҳақиқий delete).

## Автоматик изоҳлар (JE ёзувларида из)

Ҳар edit/delete ўз JE'ларига ҚИСҚА автоматик изоҳ ёзади (қўлда
киритиш талаб қилинмайди):

| Амал | Сторно JE изоҳи | Янги JE изоҳи |
|---|---|---|
| Таҳрир | «Таҳрир: INV-0012 v1→v2» | «INV-0012 v2 (таҳрир)» |
| Ўчириш | «Ўчириш: INV-0012» | - |
| Оддий сторно (мавжуд) | фойдаланувчи сабаби ёки default | - |

Шаблонлар бир жойда сақланади (Sanjar-005 Б-банди defaultIfBlank
консолидацияси билан табиий жуфт - 12 та reverse-default матни ҳам
ўша жойга йиғилади). Аудит журналида батафсил ёзув (ким, қачон,
v(n)→v(n+1)) алоҳида туради - JE изоҳи фақат қисқа кўрсаткич.

## Онгли соддалаштириш (QBO'дан фарқ ЭМАС - ички механизм)

- Ретроактив recost ЙЎҚ: янги версия ЖОРИЙ AVCO/FIFO ҳолати билан
  POST қилинади, тарих қайта ёзилмайди. Бу сторно принципининг ҳалол
  оқибати (NetSuite ёпиқ даврда, SAP доим шундай ишлайди).
  Кўринадиган хулқ QBO'га яқин, ҳисоб сиёсати консерватив - тасдиқда
  entities.md'га бир қатор изоҳ ёзилади.
- Delete GL изини ўчирмайди: нетто-ноль жуфт ёзув қолади (юқоридаги
  «Ўчириш» бўлими) - QBO'дан ягона ички фарқ, кўринадиган хулқ бир
  хил.

## Схема (changeset - навбатдаги бўш рақам, тасдиқда банд қилинади)

1-босқич жадвалларига (қуйида) тўртта устун: `revision int not null
default 1`, `superseded_by_id uuid null` (FK ўз жадвалига, SET NULL),
`deleted boolean not null default false`, ва unique(doc_number)
индексни unique(doc_number, revision) га алмаштириш. Маълумот
миграцияси керак эмас (мавжудлар revision=1, deleted=false).

## Босқичлар

- **1-босқич (шу спец кўлами, КЕНГ вариант - фойдаланувчи танлови
  2026-07-14)**: **Invoice, Bill, BankTransaction (Expense + кирим -
  битта entity), Transfer, JournalEntry, SalesReceipt** - 6 тур.
  Асос: Expense банк оиласига кирганидан reconciliation блоки
  (BR-EDT-003) барибир 1-босқичда қурилади - кирим ва Transfer
  деярли текин қўшилади; SalesReceipt application занжирисиз
  (ҳужжат+тўлов ўз ичида) - сотув томони тўлиқ қопланади.
  Умумий оркестрация shared эмас, ҳар service'да ўз
  `editPosted(...)` методи (модуллараро қоида сақланади), умумий
  қисм - версия боғлаш helper'и.
- **2-босқич**: CM/RR/VC (application занжир валидацияси билан),
  акт ҳужжатлари (StockAdjustment/StockTransfer); аудит JSON
  снапшоти.
- **3-босқич**: InvoicePayment/BillPayment (тўловни авто
  қайта-боғлаш - BR-EDT-002 юмшатилади), LandedCost (AVCO'га энг
  чуқур тегади), PayrollRun/PayrollPayment.
- **Бу механизмга КИРМАЙДИ**: Estimate/PurchaseOrder - GL'сиз,
  сторно керак эмас; уларга оддий edit очиш алоҳида кичик карта.

## Тахминий ҳажм (1-босқич)

~55-65 файл: 6 service editPosted/delete + controller/route + view
тугмалар ва версия блоклари + форма prefill йўллари + changeset +
BR каталог + messages ×3 + ҳар турга тестлар (round-trip, блоклар,
атомиклик). L/XL ҳажм - битта кучли backend coder, лекин ИККИ
тўлқинга бўлиб топшириш мумкин (аввал Invoice/Bill/JE механизм
билан, кейин банк оиласи+SR) - арбитр ПЛАНда ҳал қилади.

## Тест кутилмалари (карта очилса ПЛАНга киради)

- Ҳар тур: edit round-trip - v1 REVERSED+superseded_by тўлди, v2
  POSTED, рақам мерос, revision=2; GL: сторно JE + янги JE, ҳар
  бирида debit==credit; рўйхатда фақат v2; view'да версия занжири;
  JE изоҳларида автоматик белгилар («Таҳрир: ... v1→v2»).
- Delete round-trip: сторно JE + deleted=true; рўйхат/ҳисобот/
  қидирувда кўринмайди; trial balance ўзгармаган (нетто ноль);
  URL билан кирса «Ўчирилган» банер; рақам қайта берилмаган.
- Блок ҳолатлари (edit ва delete иккисига): тўловли invoice
  (BR-EDT-002 хабари), reconciled банк ҳужжати, ёпиқ давр санаси,
  superseded/deleted версияда амал йўқлиги (BR-EDT-006).
- Атомиклик: янги ҳужжат post'ида хато (масалан валидация) → сторно
  ҲАМ rollback (v1 POSTED лигича қолади) - мажбурий тест.
- Инвентар: ITEM сатрли invoice таҳрири - қолдиқ/қиймат тўғри
  қайтиб қайта ёзилиши; BR-INV-010 блок кейси.
- SalesReceipt: таҳрирда ҳужжат ва пул қисми БИРГА сторно бўлиб
  бирга қайта POST қилиниши (битта JE жуфти); ITEM сатрли чек ҳам.
- Банк оиласи: Transfer таҳрири (икки счёт томонлари тўғри);
  кирим/Expense фарқсиз бир хил оқимдан ўтиши.
- Жонли smoke: таҳрир → рақам ўша, суммалар янги, эски версия
  рўйхатда йўқ, версиялар ҳаволаси ишлайди; 375px.

## Қабул қилинган қарорлар (фойдаланувчи, 2026-07-14)

1. Эски версия статуси: **REVERSED + superseded_by** - янги enum
   киритилмайди (14 статус enum'ига тегилмайди).
2. 1-босқич: **КЕНГ вариант** - Invoice, Bill, BankTransaction
   (Expense+кирим), Transfer, JE, SalesReceipt (6 тур).
3. Сана: **ГИБРИД қоида** (BR-EDT-004 - сторно ва янги версия бир
   санада, очиқ давр шарти).
4. Permission: таҳрир ҳам, ўчириш ҳам ҳужжат турининг мавжуд
   **EDIT соҳасига** боғланади; алоҳида тор permission йўқ (талаб
   чиқса 2-босқичда кўрилади).
5. Ўчирилганлар учун рўйхат филтри ЙЎҚ - **аудит журнали орқали**
   етарли (рўйхатлар тоза қолади).
